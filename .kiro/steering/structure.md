# Project Structure

```
go-products-api/
├── main.go                          # Entry point: wires dependencies, registers routes, starts server
├── go.mod
├── Dockerfile
├── docker-compose.yml
├── docs/                            # Auto-generated by swag init — do not edit manually
└── internal/
    ├── domain/
    │   └── product.go               # Entity structs + repository/usecase interfaces
    ├── handler/
    │   └── product_handler.go       # HTTP layer: Gin handlers + route registration
    ├── repository/
    │   └── product_repository.go    # Data access: in-memory slice with mutex
    └── usecase/
        └── product_usecase.go       # Business logic: orchestrates repository calls
```

## Architecture

Clean Architecture with three layers, all depending inward on `domain`:

- `domain` — defines `Product`, `ProductRequest`, `ProductRepository` interface, `ProductUsecase` interface
- `repository` — implements `ProductRepository`
- `usecase` — implements `ProductUsecase`, depends on `ProductRepository` interface
- `handler` — depends on `ProductUsecase` interface; no direct repo access

## Conventions

- Interfaces are defined in `domain`, not in the implementing package
- Constructors follow `NewXxx(dep) InterfaceType` pattern, returning the interface
- Handlers use `ShouldBindJSON` for request binding with `binding:"required"` tags
- All handler errors return `gin.H{"error": "..."}` JSON
- Swagger annotations live on handler methods using `godoc` comments
- New entities should follow the same four-package pattern: domain → repository → usecase → handler
